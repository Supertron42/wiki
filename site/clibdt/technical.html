Technical overview

ClibDT6 keeps project identity, exact dependencies, compiled artifacts and release packages connected. This page explains what those checks establish and where author testing still matters.

This describes the current CLibDT6 development source used for the interface views. It does not establish that every feature is present in an older published download. Check the package version and its included documentation.

Project and library model

A project’s clibdt-project.json records its name, version, author, description and exact library pins. The shared library catalog supplies defaults for new projects. Installing a library generation does not repin existing projects.

CommonLibSSE-NG, CLibUtil and xbyak use recorded revisions and, where needed, adapter or snapshot identities. The toolkit checks the selected dependency contents. Private snapshots can preserve project-specific library changes.

Update Existing Projects prepares a review for selected projects and libraries. Updates preserve private edits by default and use verified originals for merges. Conflicts and unidentified originals need review; they are not silently replaced. Restoring a project’s version metadata does not change library pins.

Legacy import creates a separate imported copy and preserves supported exact library snapshots. Workspace connection and import are distinct workflows. Neither supplies missing C++ code or invents an adapter for an arbitrary build layout. See paths and existing projects.

The source defines the profile labels; a version appearing in the selector is a build intention, not a compatibility certification. Multi compile runs selected project/profile combinations sequentially. Test-folder copying in a batch requires one game version and the explicit copy option.

What a checked build establishes

  1. The toolkit verifies the chosen library generation and records the project’s build inputs.
  2. The build produces an x64 DLL whose plugin identity is checked against the project metadata. Matching symbols are checked when present.
  3. Verified artifacts and versioned receipts are saved under the project’s .clibdt folder, separate from installed test copies.
  4. Release rechecks the source, project metadata, dependencies and artifact hashes before using a receipt.

Changed build inputs, library contents, project metadata or DLL bytes invalidate old evidence. Compile again before packaging. Matching version changelogs are separate from DLL build inputs. Recognized successful sibling runtime lock profiles can remain valid; arbitrary lock-file edits do not.

Compile without copying to folders suppresses the primary and additional test-folder installations for that selected runtime. It still retains verified artifacts and receipts. The preference is saved separately for each game-version choice. A normal copied build deploys a complete named mod, including authored assets, rather than a lone DLL.

A receipt does not prove gameplay correctness, runtime stability or installer behavior. See compile and test copies for the practical workflow.

Release contents and publication

Plain ZIP packages include the checked DLL, authored project Data assets and matching PDB when built with debug info. Source packages can contain only src and the selected license, or explicitly include headers, resources, build definitions and exact library selections. Shared dependencies, compiler outputs and personal settings are excluded from source packages.

Saved recipes in installer/fomod.clibdt.json can produce FOMOD packages. The editor is unfinished and disabled. Recipe checks catch selected file conflicts and identify omitted authored Data assets; they do not replace installation testing in a mod manager.

Binary release archives are not silently overwritten. A same-version source archive is replaced only after the new archive is verified and the previous one is backed up. License selection does not override dependency obligations.

Local packaging does not publish. Optional Nexus publication uses a separate reviewed action, checked archive evidence and a validated key. Interrupted final publication is recorded as uncertain and is not automatically repeated. Review the Nexus Files page before resolving that state. See prepare a release.

Recovery and environment boundaries

Folder backups can use multiple source folders and exclusions. Unchanged content is stored once in a shared files store; keep that store together with the backup records. Restoration creates a new destination containing numbered source folders.

Project snapshots retain source and exact pins while excluding build caches and shared source trees. Preserve the shared Libraries store as well for offline recovery, particularly for private snapshots. See backup and restore.

Set Paths keeps unsaved edits separate from active paths. Saving selected Windows user variables does not alter the permanent global PATH. Linux builds use scoped paths and can use an explicitly sourced environment file. Linux cross-compilation requires its own compiler prerequisites and supported project adapter.

Credentials use the operating system credential store. A Nexus key is optional for local development. Source and binary package checks do not replace an author’s review of files they intend to distribute.

About the interface views

The overview’s interface images are windowless renders of the actual Rust egui screens, using an isolated copy of the current UI source. They are not illustrations or screenshots of a running desktop session. No compile, installation, release, upload or personal-settings change was performed to create them.

The views use existing workspace metadata and the configured dark theme with a teal interface accent. Display destinations were replaced with neutral workspace labels.

Versions visible in the interface are workspace versions, not a statement about the latest published releases. Batch selections and package options were staged solely to show the controls. The console is at Ready; the images contain no invented successful builds.

The implementation was checked against the toolkit’s project, library update, build, payload, release, backup and UI workflow modules. Capture work and application source stay outside this public wiki; only the reviewed images are included.
